# Model card: `fraud-detector@champion`

## Summary

| | |
|---|---|
| Model | XGBoost 2.1.4 binary classifier, trained across two Spark workers with `xgboost.spark` |
| Registered as | `fraud-detector`, alias `champion`, in the project's MLflow registry |
| Predicts | the probability that a TRANSFER or CASH_OUT transaction is fraud |
| Operating point | alert when the score is at or above 0.9478: the top 0.5% of validation scores |
| Trained on | PaySim steps 1–323 (1,951,895 in-scope transactions, 3,643 fraud), early-stopped on steps 324–377 |
| Evaluated on | PaySim steps 378–743, untouched until the final report |

## Intended use

A **portfolio demonstration** of how a transaction-fraud model is built,
validated, registered and served. It ranks transactions for review by a fraud
team with fixed capacity.

It is **not** intended for use on real payments. It was trained only on
synthetic data, and its strongest signal is an artefact of how that data was
simulated (see Limitations).

## Data

[PaySim](https://www.kaggle.com/datasets/ealaxi/paysim1): a synthetic mobile-money
log of 6,362,620 transactions over 743 hourly steps, generated by a simulator
calibrated on one month of real logs from a mobile-money service. Fraud is
0.129% of all rows and occurs only in TRANSFER and CASH_OUT, so only those
types are scored (2,770,409 rows, 0.296% fraud).

## Inputs

Ten features, all computed in `sql/features.sql` from information available
**before** the transaction's hour:

| Feature | Meaning |
|---|---|
| `log_amount` | log(1 + amount) |
| `hour_of_day`, `hour_sin`, `hour_cos` | hour of the day, raw and as a point on a 24-hour circle |
| `is_transfer` | TRANSFER (1) or CASH_OUT (0) |
| `dest_prior_txn_count`, `dest_prior_amount` | how many transactions, and how much money, the destination account received in all earlier hours |
| `dest_txn_count_24h`, `dest_amount_24h` | the same over the previous 24 hours |
| `amount_vs_dest_mean` | the amount relative to the destination's earlier average |

**Never used:** the four balance columns. They encode the simulator's
bookkeeping of the outcome ([ADR 2](../docs/decisions/0002-exclude-the-balance-columns.md)).

## Performance

Measured on the test hours with normal transaction volume (steps 378–408;
253,490 transactions, 386 fraud, 0.152%). Confidence intervals are 95%
percentile bootstraps (500 resamples).

| | Value |
|---|---|
| Average precision | 0.441 (0.395–0.493) |
| At an alert budget of 0.1% (254 alerts) | precision 61.8%, recall 40.7%, share of fraud **value** caught 79.8% |
| At an alert budget of 0.5% (1,268 alerts) | precision 17.2%, recall 56.5%, value caught 92.8% |
| Baseline: logistic regression, same features | average precision 0.090 (0.065–0.121) |
| Existing rule (`isFlaggedFraud`), whole test period | 13 alerts, all fraud, catching 0.3% of fraud cases |

After step 408, legitimate volume collapses in the simulation while fraud
continues, so the fraud rate in the remaining test hours is 2.344%. Average
precision there is 0.590 (0.576–0.605). It is reported separately because the higher
base rate inflates precision.

## Limitations

1. **Time of day carries a large share of the signal, and much of it is a
   simulator artefact.** PaySim generates fraud at a steady 144–221 cases per
   hour of the day, while legitimate volume swings from 253 to 287,916
   transactions. Retrained without any time-of-day feature, the same model's
   average precision drops from 0.441 to 0.166.
   Real fraud does skew towards the night, but not this strongly, so the
   headline figure overstates what these features would achieve on real data.
2. **Synthetic data only.** No performance figure here says anything about a
   real payment system.
3. **No fairness evaluation is possible.** The data has no customer attributes.
   A real deployment would need one.
4. **Account ids do not link transactions into chains.** Only 3 of 4,097
   fraudulent-transfer destinations ever cash out, so mule-network signals
   cannot be learned from this data.
5. **Short evaluation window.** The normal-volume test period is 31 hours with
   386 fraud cases, which is why the confidence intervals are reported.
6. **Labels are used as if known immediately.** In production, fraud labels
   arrive days or weeks later; monitoring of alert precision would lag
   accordingly.

## Serving and monitoring

The registry entry carries the feature order, the alert threshold and a
reference distribution of validation scores. The PyFlink scoring job
(`streaming/job.py`) loads all of them from `fraud-detector@champion` at
start-up, so it alerts at exactly the operating point evaluated above. Every
hour of event time it writes to InfluxDB, shown in Grafana:

- transactions scored, alerts raised, and fraud caught by alerts;
- alert precision and recall, using labels that in production would arrive later;
- score drift: the population stability index of the hour's scores against the
  validation distribution;
- dead letters (each message in the dead-letter topic records its reason).

The streaming features and scores were checked against the batch pipeline,
transaction by transaction ([ADR 5](../docs/decisions/0005-streaming-features-must-equal-batch-features.md)).
